| SSO/SAML/OIDC + SCIM | 4 | ✅ | | **OIDC shipped** (2026-07-27): authorization code flow with PKCE against any spec-compliant IdP via discovery — Google, Okta, Auth0, Entra are configuration, not code. Both vendor PATCH shapes are handled because both are in the wild — Okta's pathless `{op:"replace",value:{active:false}}` and Entra's `{path:"active",value:"False"}` with a *string*. **The substantial half was making deprovisioning mean something:** `User.status` existed in the schema but was checked nowhere, so `active:false` would have been decorative. Withdrawn access now ends everywhere at once — the workspace membership is removed, every refresh session is revoked, live sockets are disconnected (a socket authenticates once at handshake, so it would otherwise outlive its access), an already-issued access token stops working within the same request, and password and SSO sign-in both refuse with the actual reason rather than "bad credentials". Tokens are `yscim_`-prefixed 256-bit secrets stored only as SHA-256, shown once on creation, revocable, and never returned by any read. Owner-only, with a Directory sync tab in the admin console. 59 checks pass end-to-end against a live server with real Mongo and Redis, including the two-tenant cases: one workspace's token cannot read or deprovision another's user, and deprovisioning someone who belongs to two workspaces removes them from one without suspending the account they still legitimately use. **SAML 2.0 shipped (2026-07-30):** Web Browser SSO — HTTP-Redirect out, HTTP-POST back — alongside OIDC, chosen per provider from `SAML_PROVIDERS` and offered as one merged list on the login page. **This one uses a library where OIDC was hand-rolled, deliberately:** an ID token is a signature over a compact byte string, but a SAML signature is over an XML *tree* verified after exclusive canonicalisation, and nearly every historic SAML break is signature wrapping — a mismatch between the element verified and the element read. Writing C14N here would have put that mismatch in this repo, so `@node-saml/node-saml` owns the signature and this code owns everything above it. Each provider gets **its own SP entityID and ACS URL**, so an assertion minted for one configured IdP cannot be spent at another's endpoint. `InResponseTo` is required and its request id is held in **Redis** — node-saml's in-memory default would refuse any response landing on a different process than the one that started the flow, turning a security control into an intermittent failure operators would switch off — and consuming the id on use is what makes a replay fail. Assertions must always be signed; requiring the envelope signature too is per-provider, since most IdPs sign only the assertion. **A real gap found while testing:** the library's `idpIssuer` option is only consulted for *logout* messages, so a configured expected issuer did nothing on the sign-in path — that would have been a decorative setting, so the check is now made here against the signed assertion's issuer. SAML has no `email_verified`, so the account-takeover rule (link to an existing account only on a trusted address) is answered by an explicit per-provider `TRUST_EMAIL`, off by default; provisioning a *new* person is allowed regardless, because an address nobody holds takes nothing over and onboarding is what an enterprise IdP is for. The identity rules now live in one module shared with OIDC so the two cannot drift. Not implemented, and said rather than implied: single logout, IdP-initiated sign-in (no AuthnRequest to bind to), encrypted assertions. **31 checks pass end-to-end against a stub IdP with a real RSA keypair and genuine XML-DSig**, most of them attacks: unsigned assertion, wrong signing key, attribute tampered after signing, NameID tampered after signing, **signature wrapping**, wrong audience, expired, not-yet-valid, forged issuer, unsolicited, cross-provider replay, replayed response, three open-redirect payloads, a forged RelayState, refused takeover of an existing account, permitted link on a trusted provider, and a deprovisioned account refused a way back in |

| Data residency | 4 | ✅ | | Shipped 2026-07-30. A deployment declares its own region (`REGION`) plus the fleet it can point at; a workspace is pinned to the region of the deployment that created it and can never be moved, because the rows are already written by then and a later change would relabel data that has not moved. **The enforcement is the substance:** `settings.dataResidencyRegion` was declared in schema.md at v1.0 and read by nothing, so it would have been a label. | E2EE sensitive-project mode | 4 | ✅ | | Shipped 2026-07-30. Chosen at creation and immutable thereafter — flipping it either way would leave documents written under the opposite assumption in the same log. | 2026-07-30 | A Delve command that runs the program waits for a new position or the process exiting, not merely for the prompt | Delve can write its prompt *before* the "Process N has exited" notice, so a `continue` that ran to completion looked finished while the room still showed "paused" — and the exit notice then turned up as the answer to the next `stack` query. This is the third time a debugger's prompt has proved to mean less than it appears (`node inspect`, jdb, now Delve), and the `executing` flag on `findPrompt` exists precisely for it. Only the end-to-end test could see it | debugger.ts |
| 2026-07-30 | SAML's XML-DSig comes from a library (`@node-saml/node-saml`), where OIDC was written out in full | The OIDC verification is a signature over a compact, unambiguous byte string, and node ships everything it needs — writing it out left nothing to guess. A SAML signature covers an XML *tree* after exclusive canonicalisation, and essentially every historic SAML break is signature wrapping: the element verified is not the element read. Hand-rolling C14N would have put that failure mode in this repo, and the reviewable choice is the maintained implementation that reads the signed assertion rather than re-querying the document. The protocol decisions above it — issuer, audience, replay, identity — stay here | saml.ts |
| 2026-07-30 | The expected IdP issuer is checked in our own code, not by the library's `idpIssuer` option | Reading the installed version showed that option is consulted only for logout messages, so a configured expected issuer had no effect on sign-in — a setting that looks like a control and is not one, which is the exact failure this codebase keeps refusing to ship. It is now compared against the *signed* assertion's issuer, so it is the IdP's authenticated claim rather than an envelope value an attacker chooses. Caught by a test written to assert the behaviour the configuration promised | saml.routes.ts |
| 2026-07-30 | Each SAML provider gets its own SP entityID and ACS URL, and AuthnRequest ids live in Redis | One shared entityID would let an assertion minted by one configured IdP be replayed into another's ACS endpoint; per-provider audiences make that fail (tested). And node-saml's in-memory request cache would refuse any response that lands on a different process than the one that started the flow — turning replay protection into an intermittent sign-in failure that an operator would eventually switch off. Consuming the request id on use is also what makes a replayed response fail | saml.ts |
| 2026-07-30 | SAML linking to an existing account requires an explicit per-provider `TRUST_EMAIL`; provisioning a new account does not | SAML has no `email_verified`, so the rule OIDC leans on has no equivalent to read — the deployment has to state it. The two halves are not equally dangerous: attaching an IdP identity to an account that already exists hands over that account, while creating one for an address nobody holds takes nothing over, and refusing it would leave an enterprise IdP unable to do the onboarding it exists for. Both protocols now resolve identities through one shared module, so the rule cannot drift between them | ssoIdentity.ts, saml.routes.ts |
| 2026-07-30 | Point-in-time recovery records the oplog position *before* the dump and replays across the dump window, rather than using mongodump's `--oplog` | `--oplog` is refused on any dump whose connection string names a database, and Yumi's always names one, so the option that exists for exactly this purpose is unavailable. Recording the position first and replaying forward reaches the same place: oplog entries are idempotent by construction — it is how a secondary re-applies them — so replaying operations the dump already contains is safe rather than merely tolerable | scripts/backup.mjs, scripts/restore.mjs |
| 2026-07-30 | Archived oplog entries are copied as raw BSON, never decoded and re-encoded | The driver promotes the entry's `t` (election term) from a BSON Long to a JS number, which re-serialises as an int32, and the server then refuses the whole replay with "BSON field 'OpTimeBase.t' is the wrong type 'int', expected type 'long'". Copying the bytes verbatim cannot introduce that class of problem at all — and it is a class, not one field, since any Long anywhere in an entry would do the same | scripts/oplog-archive.mjs |
| 2026-07-30 | The oplog archiver refuses to continue a chain the oplog has rolled past | The oplog is capped, so a chain is only unbroken if it is extended faster than the oplog turns over. Writing a segment across a gap would produce a backup that looks complete and silently skips an hour — the worst possible outcome, because it is discovered during a recovery. It stops and says to take a fresh base backup instead | scripts/oplog-archive.mjs |
| 2026-07-30 | A backup records the regions its data is pinned to, and a restore into a different region is refused unless forced | Every runtime path refuses out-of-region access, but a restore bypasses all of them: it writes whatever the archive holds into whatever database `MONGO_URI` names, with nothing running to object. The regions are read from the workspaces themselves rather than from the environment of whoever ran the backup, so the archive describes its own contents. Verified all three ways: refused with `REGION` unset, refused with the wrong region (naming the right one), and passed through to the ordinary populated-database guard when they match | scripts/backup.mjs, scripts/restore.mjs, dr.md |
| 2026-07-30 | A workspace is pinned to the region of the deployment that creates it, and the pin is immutable | That deployment's database is where the insert actually lands, so it is the only region the pin can honestly name. Accepting a request to create an EU workspace from the US tier would write the rows in the US and label them as living in the EU, which is worse than refusing. And afterwards the data already exists: changing the field would move nothing, so the setting would mean "from now on", which is not what anyone reads it as | workspace.routes.ts, residency.ts |
| 2026-07-30 | A pinned workspace is refused by every other region on **all** paths, reads included, with 421 and the right region's address | The realtime path is where document contents actually travel, so a REST-only check would refuse the page listing the files while the editor synced happily; SCIM writes accounts and memberships unattended; and an invite is opened wherever the recipient's browser resolves. Reads are included because serving a pinned workspace's contents from another region moves them out of it just as surely as writing would. 421 says "wrong door" — a 403 or 404 would be actively misleading about data the caller may legitimately hold | middleware.ts, gateway.ts, scim.routes.ts, invite.routes.ts |
| 2026-07-30 | The region check runs *after* the membership check, never before | Otherwise every endpoint becomes an oracle: a stranger could ask about any workspace id and learn from the response shape whether it exists and which region holds it. A non-member gets the same 403 they always did; only someone with legitimate access is told where to go instead | middleware.ts |
| 2026-07-30 | A pinned workspace on a deployment that declares no region is a mismatch, not a pass | Failing open elsewhere in this codebase (the suspension fast-path) was justified by a bounded, recoverable exposure. This one is neither: a process that cannot name where it stores data would write a customer's data to an unknown jurisdiction, and data written to the wrong country cannot be un-written once noticed. A malformed `REGION` therefore stops the process at boot rather than surfacing per-request | residency.ts, index.ts |
| 2026-07-30 | Features that hand contents to a third party are refused in a pinned workspace unless an operator declares otherwise | Pinning storage does not pin processing. The AI, GitHub, Figma and Slack all send workspace contents outside the region whichever database the rows sit in, so a residency promise that quietly excluded them would be a promise about the easy half. `AI_REGION` declares an in-region model endpoint (the honest path); `RESIDENCY_ALLOW_EGRESS` records that an organisation accepts the rest leaving. Slack is re-checked at send time, because a link can outlive the policy that permitted it | residency.ts, project.routes.ts, gateway.ts |
| 2026-07-30 | The AI's residency refusal is checked before the "is an API key configured" check | The same reason as the E2EE ordering: otherwise a deployment without a key sends the operator to configure something that still would not make the assistant available in that workspace. Verified explicitly in testing, with no key set anywhere | gateway.ts |
| 2026-07-30 | The workspace list omits foreign-region workspaces and returns a count plus where to go | A workspace's *name* is its customer's data too, so listing every name on every regional tier would leak exactly what pinning exists to contain. A count and a link are enough for the dashboard to say "you have 2 workspaces in the EU" without any of them crossing the border to say it | workspace.routes.ts |
| 2026-07-30 | The cross-region screen is never an automatic redirect, and its link only ever comes from the server's own region registry | Sending a browser to another host unasked is indistinguishable from a hijack, and the person probably wants to know why their bookmark stopped working. Building the target from server config rather than anything the caller supplied is what stops the refusal being turned into an open redirect — the same lesson as the SSO `returnTo` rule | region.tsx, residency.ts |
| 2026-07-30 | Cross-region and blocked-egress audit entries are deduplicated per workspace+user for ten minutes | A misconfigured client retries on a timer, and an audit log flooded by one loop is a log nobody can read — which would destroy the value of the entry that matters, the first one. Verified: three further attempts add nothing | residency.ts |
| 2026-07-29 | SCIM deprovisioning withdraws *workspace* access, and suspends the account itself only when the user has no workspace left | A Yumi account is global — one person, many workspaces — while a SCIM token belongs to one workspace. Suspending outright on one tenant's instruction would let it lock a user out of a different tenant's workspace, which is an authority that tenant does not have. The ordinary single-tenant case still gets full offboarding, because "no workspace left" is exactly what happens there | scim.routes.ts |
| 2026-07-29 | `User.status` is now enforced at every point access is granted, not just recorded | The field existed from the initial schema and was read nowhere, so `active:false` would have changed a database row and nothing else. Deprovisioning is the entire reason an enterprise buys SCIM, so it withdraws membership, revokes every refresh session, disconnects live sockets, and is checked on password sign-in, SSO sign-in, refresh, and each authenticated request | middleware.ts, auth.routes.ts, sso.routes.ts, gateway.ts |
| 2026-07-29 | The suspension fast-path lives in Redis and fails **open**, loudly | An access token is verified locally with no database read, so without a marker a deprovisioned user keeps working for up to the token lifetime. Failing closed would sign everyone out during a cache blip; failing open costs at most one access-token lifetime, and only in an outage where no new token could be issued anyway (refresh sessions live in the same Redis). The choice is logged rather than silent | middleware.ts, auth.ts |
| 2026-07-29 | `userName` is immutable through SCIM, and rejected with a reason rather than ignored | It is the account's login identity in every workspace, so honouring a rename from one tenant would rewrite how that person signs in to all the others — and a directory that could set an arbitrary address is a takeover primitive. Answering 400 with the reason is better than a silent no-op that leaves the IdP believing it succeeded | scim.routes.ts |
| 2026-07-29 | An unsupported SCIM filter is a 400, never a match-all | A filter quietly ignored turns "does this one user exist?" into a dump of the whole member list. Only `eq` on userName/externalId/active is supported, which is what IdPs actually send on a user sync | scim.routes.ts |
| 2026-07-29 | Users only, no Groups; the SCIM token cannot change roles, and never demotes | `/ResourceTypes` advertises User alone, so a client discovers the limit at configuration time instead of failing mid-sync. Role stays an owner's decision in the console: a directory that could assign roles would move authorisation out of the product and into whoever administers the IdP, and a later sync could silently reset a hand-promoted owner | scim.routes.ts |
| 2026-07-29 | The SCIM token is compared by SHA-256, not a password KDF, and the last owner cannot be deprovisioned | The token is 256 bits of server-generated randomness, so there is nothing to brute-force and a deliberately slow hash on every provisioning call would just be a way to exhaust the server — unlike a password, which is low-entropy by nature. And removing the only owner would leave a workspace nobody can administer, so it is refused with instructions instead | scim.routes.ts |
| 2026-07-28 | Java debugs through the JDK's `jdb`, and an executing command waits for a *suspended* prompt rather than any prompt | jdb answers `cont`/`step` with its idle `> ` prompt straight away and prints "Breakpoint hit:" only when the program actually stops, so treating any prompt as "command finished" would hand the room a stale position — the same failure that made `node inspect` unusable. Waiting for the `main[1] `-shaped prompt (or the application exiting) makes it as synchronous as pdb | debugger.ts |
| 2026-07-28 | The prompt contract moved into the Adapter as `findPrompt(buf, executing)`, and each adapter now normalises its own file paths | One fixed prompt string worked only because pdb has exactly one. Pushing the decision into the adapter is what let jdb join at all, and it removed the session's hardcoded `/work/` filter — which was Python's container layout leaking into shared code, and would have silently dropped every Java frame | debugger.ts |
| 2026-07-28 | Java compiles with `javac -g`, and the entry stop at `Main.main` is hidden from the breakpoint list | Without `-g` jdb answers `locals` with "Local variable information not available" — a debugger that can't show variables isn't worth shipping. And jdb never halts on its own, so an internal breakpoint at the entry point gives Java the same "paused on the first line" start as every other language; showing it as a user breakpoint would invite someone to clear it and lose the start pause | debugger.ts |
| 2026-07-28 | C++, Go and Rust debugging is blocked on the sandbox images, not deferred by choice | `gcc:14`, `golang:1.23-alpine` and `rust:1-alpine` contain no debugger — `rust-gdb` is a wrapper script that execs a `gdb` that isn't installed — and `--network none` (rules.md §3.5) means nothing can be fetched at run time. Java is debuggable only because the JDK image happens to ship `jdb`. Supporting the rest means building sandbox images with gdb/delve baked in, which is an infrastructure decision with its own image-size and trust questions | debugger.ts |
| 2026-07-28 | The harness detaches the inspector *before* reporting that the program exited, and `start()` fails with the program's own words | Node keeps a dying process alive while a debugger is attached ("Waiting for the debugger to disconnect...") and writes the uncaught error only after it lets go — so reading the output first reported that the program stopped but never why. A file that can't compile used to hang for the full 45s ready timeout and then say "the debugger did not become ready in time"; it now reports node's actual error in about a second | debugHarness.mjs, debugger.ts |
| 2026-07-27 | One debug session per project, shared by the whole room; editors drive, viewers watch; expression evaluations go only to the asker | A debugger everyone can watch is the actual feature — two independent sessions would just be two people debugging alone. Evaluations are questions rather than state changes, so broadcasting them would be noise | gateway.ts, DebugPanel.tsx |
| 2026-07-27 | Breakpoints and the paused line reach CodeMirror as StateEffects, not props | The editor is rebuilt only on doc/language/editability changes; pushing debugger state through props would tear down and re-create the Yjs binding on every step | debugGutter.ts, CodeEditor.tsx |
| 2026-07-27 | A debug session deregisters itself on close, and its container is killed on room-empty, on a 20-min TTL, and on server shutdown | Unlike the one-shot runner, a debug container lives as long as the session — a leaked one holds memory and a CPU share indefinitely. Leaving a finished session in the registry also made the next command find a dead session instead of reporting none (caught in testing) | debugger.ts, gateway.ts, index.ts |
| 2026-07-27 | Slack event defaults are failure-biased (run fails / tests fail), and the webhook URL is treated as a credential — never returned, only `hasWebhook` | A channel that pings on every join gets muted, and a muted channel notifies nobody; and anyone holding an incoming-webhook URL can post to that channel, so it gets the same treatment as the GitHub/Figma tokens | SlackModal.tsx, project.routes.ts |
